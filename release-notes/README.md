# Ноты релизов (до тега)

Каждая версия описывается здесь **до** постановки тега: файл называется по тегу
(`v0.8.4.md`, `v0.8.4-rc.2.md`), а его текст — это будущее тело релиза на GitHub
и будущая запись версии в [CHANGELOG.md](../CHANGELOG.md).

## Зачем каталог, а не страница релиза

`npm run changelog:sync` берёт ноты версии со страницы релиза — но релиза не
существует, пока не поставлен тег. Пока запись в CHANGELOG создавалась после
тега, она оказывалась **вне** дерева тега: `git show v0.8.3:CHANGELOG.md` не
содержал v0.8.3, то есть в дереве, из которого собран релиз, своей версии нет.
Репозиторий же может описать релиз, которого ещё нет на GitHub — это и делает
файл нот.

## Как это работает

```
release-notes/v0.8.4.md
        │
        ├─ changelog:sync до тега  → запись «## v0.8.4 — дата · Ожидает тега»
        │                            (в дереве коммита, на который встанет тег)
        ├─ workflow Release: release-publish с телом из этого же файла
        │                            → тело релиза на GitHub
        └─ workflow Release: changelog:sync после публикации
                                     → GitHub выигрывает: канал меняется на
                                       «Latest» / «Pre-release», текст тот же
```

Релизный скрипт (`scripts/release-prepare.mjs`) режет релиз в порядке
«бамп → CHANGELOG → тег», а `scripts/release-publish.mjs` не выпустит тег, в
дереве которого записи нет.

## Если файла ещё нет: черновик вместо отказа

`npm run release:prepare -- --version 0.8.4` при отсутствии файла **не падает**, а
собирает черновик и останавливается: ноты не должны начинаться с пустой страницы.

Что в черновике:

- первая строка — маркер `> **Черновик нот.**` с указанием диапазона и числа
  коммитов;
- разделы по типам коммитов (✨ Новое, 🐛 Исправления, 📚 Документация, …) и
  ссылка на каждый коммит;
- ссылка на сравнение с предыдущим релизом в конце.

**Диапазон.** Для кандидата (`0.8.4-rc.2`) берётся предыдущий тег любого вида
(им окажется `v0.8.4-rc.1`), для стабильной версии — предыдущая **стабильная**, то
есть вся дельта, которую получает стабильный канал (`v0.8.3`).

**Что делать дальше.** Перепишите разделы в прозу, добавьте в начало абзац-суть и
удалите строку с маркером, затем запустите ту же команду снова. Пока маркер на
месте, версия не режется и не публикуется: автособранные подписи коммитов
(`fix(console): печатать…`) — не то, что должен читать пользователь.

## Правила

- **Имя файла = тег.** `v0.8.4.md` соответствует тегу `v0.8.4`. Файлы с другим
  именем (`README.md`, `draft.md`) генератор игнорирует.
- **Текст начинается с абзаца-сути.** Строку вида `# HueForge Web v0.8.4 — …`
  генератор превратит в подзаголовок курсивом, поэтому заголовок с версией
  писать не нужно: он и так стоит в CHANGELOG. Внутри используйте `##` и `###`.
- **После публикации файл замораживается.** В CHANGELOG идёт тело релиза с
  GitHub; если файл и тело разошлись, `changelog:sync` напечатает предупреждение
  и всё равно возьмёт версию со страницы релиза.
- **Пустой файл — не запись.** Заготовка без текста ничего не добавляет в
  CHANGELOG, а `release:prepare` откажется резать релиз.
- **Непереработанный черновик — тоже не запись.** Файл, полученный генератором,
  отличается от написанного только маркером — его и убирают в конце правки.
- **Файл остаётся в репозитории** и после публикации: по нему видно, что именно
  обещали в версии, не открывая GitHub. А вот файл версии, которая так и не была
  выпущена, надо удалить: пока файл есть, CHANGELOG показывает её как «Ожидает
  тега».
