# Разворачивание HueForge Web (deploy)

Готовый пакет `hueforge-web-deploy-v*.zip` — это **собранное приложение**:
не нужны ни `npm install`, ни интернет, ни исходники. Только Node.js.

> **Предпочитаете обычное приложение?** Есть и настольная версия — установщик
> `hueforge-desktop-setup-<version>.exe` с того же релиза: окно с ярлыком, автообновление
> из GitHub Releases, нативные диалоги сохранения. См. раздел «Настольное
> приложение (Electron)» в README. Этот файл — про вариант «сервер + браузер».

## Разворачивание на новом ПК

1. Установите [Node.js LTS](https://nodejs.org) (один раз, на весь ПК).
2. Распакуйте `hueforge-web-deploy-v*.zip` в любую папку.
3. Дважды щёлкните **`deploy.bat`** — сервер запустится и откроется браузер на
   `http://127.0.0.1:8080`.

Закройте окно консоли — сервер остановится. Другой порт: `deploy.bat 3000`.

## «Открыть в слайсере» (по желанию)

`deploy-slicer.bat` — то же самое, но с включённой передачей в слайсер:
кнопка **«Открыть в слайсере»** в разделе экспорта отправит собранный 3MF
сразу в установленный слайсер (Bambu Studio / OrcaSlicer / PrusaSlicer).

- По умолчанию функция **выключена** — обычный `deploy.bat` её не включает.
- Сервер слушает только `127.0.0.1`, и запустить чужой exe из запроса нельзя:
  приложение выбирает лишь среди слайсеров, найденных на этом компьютере.
- Слайсер не нашёлся? Укажите путь вручную перед запуском:
  `set HF_SLICER_PATH=C:\Path\To\slicer.exe` (или JSON-массив
  `set HF_SLICER_PATH=["C:\Path\slicer.exe","--flag"]` — аргументы передаются
  перед файлом модели).
- В исходниках то же самое: `set HF_ALLOW_SLICER=1` перед `npm run dev`.

Эквивалент ручного запуска: `node server.mjs 8080 --allow-slicer`.

## Как собрать такой пакет из исходников

```bash
npm run build          # создаёт dist/
npm run pack-deploy    # собирает hueforge-web-deploy-v<версия>.zip
```

`pack-deploy` кладёт в архив только то, что нужно для работы:
`dist/`, `server.mjs`, `slicer-launch.mjs`, `deploy.bat`,
`deploy-slicer.bat`, `install.bat`, `update.ps1` и этот файл.

## Чек-лист обновления со старой версии

1. **Остановите старый сервер** — закройте окно консоли, где работает
   `deploy.bat` (или нажмите Ctrl+C в нём).
2. **Скачайте новый пакет** `hueforge-web-deploy-v0.8.2.zip` с GitHub
   (страница релизов) — или возьмите свежую сборку, если вам её передали
   напрямую.
3. **Распакуйте архив поверх старой папки** (или в новую папку — оба
   варианта подходят).
4. **Запустите `deploy.bat`** и дождитесь, пока откроется браузер на
   `http://127.0.0.1:8080`.
5. **Проверьте версию** в шапке приложения — должно быть «v0.8.2».
6. **Проверьте свои настройки**: язык, тема, выбранный принтер и палитра
   хранятся в браузере и сохраняются между обновлениями. Если открылся
   «чистый» вид — вы открыли приложение в другом браузере или профиле;
   настройки привязаны к браузеру, а не к файлам приложения.
7. **Быстрая проверка работы**: загрузите картинку → палитра построится →
   скачайте STL или 3MF → убедитесь, что кнопки панелей не выходят за
   границы.

Если что-то пошло не так, всегда можно вернуться: распакуйте предыдущий
архив и запустите его `deploy.bat` — старые версии пакетов совместимы.

## Обновление из исходников (необязательно)

В пакете есть и классический установщик-обновлятор **`install.bat`** (с
помощником `update.ps1`). Он нужен, если вы хотите получать свежие версии
прямо с GitHub в один клик: проверяет, вышла ли новая версия, скачивает
исходники, ставит зависимости и создаёт ярлык на рабочем столе.

1. Запустите **`install.bat`** из распакованной папки.
2. При первом запуске он может попросить **GitHub-токен** — репозиторий
   приватный, поэтому проверка обновлений без токена невозможна. Создайте
   fine-grained токен (доступ только к этому репозиторию, права
   `Contents: Read` + `Metadata: Read`) и введите его один раз — он
   сохраняется только на этом ПК (в `%APPDATA%\HueForgeWeb`).
3. Дальше при каждом запуске `install.bat` сам спросит: обновиться до новой
   версии или работать с текущей.

**Важно:** `install.bat` переводит папку в режим «из исходников» — после
первого обновления это полноценная установка с исходным кодом и dev-сервером
(нужны Node.js и интернет), а не готовый пакет. Обычным пользователям
достаточно `deploy.bat` и ручного обновления по чек-листу выше; `install.bat`
подходит тем, кто хочет автообновления с GitHub.

Первый запуск `install.bat` в свежей deploy-папке сразу предложит обновление:
номер версии определяется из исходников, которых в пакете ещё нет — примите
его, и папка станет актуальной установкой.

### update.ps1 вручную

Тот же помощник можно вызывать напрямую из PowerShell (из распакованной
папки). Команды:

- `powershell -ExecutionPolicy Bypass -File update.ps1 check` — печатает
  номер новой версии (например `v0.8.2`), если она вышла, `NEED_TOKEN` —
  если репозиторий требует токен, или ничего — если обновлений нет.
- `powershell -ExecutionPolicy Bypass -File update.ps1 save-token` —
  попросит ввести токен (ввод маскируется) и сохранит его в
  `%APPDATA%\HueForgeWeb\github_token.txt`.
- `powershell -ExecutionPolicy Bypass -File update.ps1 download v0.8.2` —
  скачает исходники версии `v0.8.2` с GitHub во временную папку и напечатает
  путь к распакованному дереву (его можно скопировать поверх текущей папки).
- `powershell -ExecutionPolicy Bypass -File update.ps1 download-deploy v0.8.2` —
  **обновление для пользователей deploy-пакета**: скачает готовый пакет
  `hueforge-web-deploy-v0.8.2.zip` с релиза и распакует его **поверх текущей
  папки** (без исходников, без npm install). После этого нужно перезапустить
  `deploy.bat`. Команда заменяет и сам `update.ps1` на новую версию, поэтому
  её можно запускать повторно в каждой новой версии.
- `powershell -ExecutionPolicy Bypass -File update.ps1 rollback` — **откат**:
  вернёт папку в состояние до последнего обновления. Перед распаковкой
  `download-deploy` сохраняет бэкап предыдущей версии в
  `%APPDATA%\HueForgeWeb\backup-deploy` (один слот — состояние до последнего
  обновления); `rollback` восстанавливает его. Откат зеркальный: файлы,
  добавленные обновлением (например, новые бандлы `dist/`), удаляются —
  папка возвращается ровно в прежнее состояние. Если бэкапа нет — команда
  сообщит об ошибке.

> **Чистая замена `dist/`:** `download-deploy` зеркалит папку `dist`
> (`robocopy /MIR`) — устаревшие файлы сборки старой версии удаляются, а не
> копятся. Файлы вне `dist/` (например, сохранённые вами конфиги) при
> обновлении не трогаются; при откате возвращается точное прежнее состояние.

Токен вместо сохранения можно задать и переменной окружения
`HF_GITHUB_TOKEN` — она имеет приоритет над файлом.

> **Важно про версии:** в deploy-пакете нет `package.json`, поэтому его версия
> лежит в файле `version.txt` (внутри пакета). Команда `check` читает его,
> чтобы понять, обновлялась ли папка — не удаляйте этот файл.

### GitHub-токен: как создать

Обновления ходят через GitHub API: без токена работает только анонимный доступ
(его хватает для публичного репозитория, но у него низкий лимит запросов — как
и у `install.bat`, токен лишь поднимает лимит). Один раз:

1. Откройте [GitHub Settings → Fine-grained tokens](https://github.com/settings/personal-access-tokens)
   и нажмите **Generate new token**.
2. В **Repository access** выберите **Only select repositories** → `Sovero/hf`.
3. В **Permissions** → **Repository permissions** поставьте:
   - **Contents**: **Read-only**
   - **Metadata**: **Read-only** (GitHub требует его автоматически)
4. Создайте токен и скопируйте его (показывается один раз).
5. Введите его в `update.ps1 save-token` — или запустите `install.bat` и
   согласитесь на ввод токена при первом запуске.

Токен хранится только на этом ПК, в `%APPDATA%\HueForgeWeb\github_token.txt`,
и даёт доступ только на чтение этого репозитория. Если токен засветился или
больше не нужен — отзовите его на той же странице GitHub (Revoke).

## Для разработчиков

- `npm run serve` — тот же сервер для локальной проверки сборки (`node server.mjs`).
- `install.bat` / `start.bat` из репозитория запускают **dev-версию** (с исходниками
  и `node_modules`) — для доработки. Пакет deploy — для использования.
- **Сообщения запуска печатает PowerShell, а `.bat` — только ASCII-код.**
  `cmd.exe` разбирает командный файл в текущей кодировке и срывается на
  многобайтных символах: файл с кириллицей ломает сам парсер (даже строки `REM`
  в начале файла разбираются неверно), и это воспроизводится независимо от CRLF
  и переключения на `chcp 65001`. Поэтому `.bat` (`install.bat`, `start.bat`,
  `deploy.bat`, `deploy-slicer.bat`) содержит только латинский код, а русский
  текст вызывает из `update.ps1`:

  ```bat
  call :say install.deps "%NEW_VERSION%"
  :: → powershell … update.ps1 say install.deps v0.9.0
  ```

  Таблица текстов (ключ → строка, с подстановками `{0}`) лежит в `update.ps1`
  (UTF-8 с BOM — PowerShell читает его корректно). Цена — запуск PowerShell на
  каждое сообщение (≈0,3 с), поэтому в одном сообщении держите все строки
  одного блока, а не по строке на вызов. `src/test/consoleMessages.test.ts`
  проверяет, что `.bat` остаётся ASCII, ключи совпадают с таблицей и число
  аргументов хватает на подстановки. Тексты интерфейса приложения — в
  `src/i18n.ts`. `.gitattributes` закрепляет для `*.bat`/`*.cmd` переводы строк
  CRLF — с LF-переводами `cmd` тоже разбирает файл неверно.

### Публикация релиза: стабильный канал и RC

Приложение следит только за **последним стабильным** релизом: оно запрашивает
`releases/latest`, а GitHub исключает оттуда pre-release. Поэтому релиз-кандидат
обязан публиковаться с флагом pre-release.

Порядок шагов задан жёстко: **ноты → бамп → CHANGELOG → тег → публикация**.
Запись версии обязана попасть в коммит **до** тега: иначе её нет в дереве, из
которого собран релиз, и `git show v0.8.4:CHANGELOG.md` показывает версию,
которой в файле нет — так вышло у всех уже выпущенных версий.

```bash
# 1. Опишите релиз. Имя файла — тег; этот же текст станет телом релиза на GitHub
$EDITOR release-notes/v0.8.4.md

# 2. Бамп версии, запись в CHANGELOG и тег — одной командой, именно в этом порядке
npm run release:prepare -- --version 0.8.4

# 3. Пуш коммитов и тега: CI соберёт черновик релиза с артефактами
#    (нужна локальная сборка вместо CI — npm run dist, exe + blockmap + latest.yml)
git push origin main v0.8.4

# 4. Публикация черновика с флагами канала и проверками
npm run release:publish
```

Пуш остаётся ручным: `release:prepare` только печатает команду.

Шаг 3 повторяет ту же проверку в CI: workflow **Release** первым делом сверяет
тег с `package.json` и с записью в `CHANGELOG.md`, и тег без записи не дойдёт
даже до сборки артефактов.

`scripts/release-prepare.mjs` режет релиз по шагам и останавливается при любом
сомнении:

- требует `release-notes/<тег>.md`: если файла нет, сам собирает черновик из
  коммитов между тегами — для стабильной версии от предыдущей стабильной, для
  кандидата от предыдущего тега, — печатает диапазон и **останавливается**;
  черновик помечен строкой «Черновик нот», и пока она в файле, ни этот скрипт, ни
  публикация не выпустят релиз по автособранному тексту (подробности — в
  `release-notes/README.md`);
- проверяет ветку `main`, синхронизацию с `origin/main` и что тег свободен и
  локально, и на origin; посторонние незакоммиченные правки — отказ, а вот ноты
  выпускаемой версии могут быть не закоммичены: их коммитит сам релиз;
- поддерживает `--dry-run`: печатает весь план и ничего не меняет;
- бампит версию в `package.json` и `package-lock.json` и коммитит бамп — дата
  этого коммита датирует запись в CHANGELOG;
- синхронизирует CHANGELOG **до** тега и падает, если записи не появилось
  (бамп при этом уже закоммичен — повторный запуск той же команды его пропустит);
- ставит лёгкий тег и сверяет, что и версия, и запись видны в дереве тега.

`scripts/release-publish.mjs` делает всё, на чём легко ошибиться вручную:

- проверяет, что тег есть на origin, что в его коммите та же версия, что в
  `package.json` (артефакты принадлежат тегу, а не рабочему дереву), и что
  **в дереве тега есть запись этой версии в `CHANGELOG.md`** — публикация
  падает, если порядок был нарушен;
- берёт тело релиза из `release-notes/<тег>.md` и сверяет его с опубликованным:
  страница релиза и запись в CHANGELOG говорят одно и то же, а не расходятся с
  авто-нотами GitHub; файл с непереработанным черновиком отвергается;
- берёт файлы из одного из двух источников: локальная сборка `release/` — тогда
  sha512 в `latest.yml` сверяется с самим exe и файлы заливаются; или черновик,
  который собрал CI — тогда ничего не заливается, а проверяется уже загруженный
  `latest.yml`: версия, наличие sha512 и совпадение размера с exe на релизе;
- сам выставляет `--prerelease` тегу с суффиксом (`v0.8.3-rc.5`) и `--latest`
  стабильному (`v0.8.3`);
- заливает exe, blockmap и `latest.yml`, а затем скачивает `latest.yml` обратно
  и сверяет с собранным;
- **падает с ненулевым кодом**, если `releases/latest` указывает на кандидата,
  и печатает команду для починки.

Полезные режимы: `--dry-run` (показать команды, ничего не менять), `--notes FILE`
(взять тело релиза не из `release-notes/`, а из другого файла), `--version X.Y.Z`
(публиковать не текущую версию). Если нужно сначала посмотреть артефакты — создайте
черновик (`gh release create vX.Y.Z --draft --verify-tag`), скрипт его опубликует.

Если RC всё же опубликован как обычный релиз, он станет «latest» и уйдёт на
**все** стабильные установки по автообновлению (так вышло с `v0.8.3-rc.4`).
Починка вручную: `gh release edit <rc-тег> --prerelease`, затем
`gh release edit <стабильный-тег> --latest`. Workflow
`.github/workflows/release.yml` выставляет флаг автоматически по тегу — но только
когда CI запускается. RC-установки получают следующую **стабильную** версию,
стабильные — никогда RC.

`npm run changelog:sync` (нужен авторизованный `gh`) перегенерирует раздел
релизов в [CHANGELOG.md](CHANGELOG.md) — версии, даты, каналы и тела релизов
дословно. После публикации он нужен лишь затем, чтобы в записи «Ожидает тега»
заменилось каналом релиза: сами ноты уже лежат в дереве тега, а GitHub отдаёт
ровно тот же текст из `release-notes/<тег>.md`. Если у релиза своих нот нет,
разделы собираются из коммитов между тегами: по типам (`feat`, `fix`, `ci`, …),
со ссылкой на каждый коммит и с честно указанным диапазоном тегов. Запись
версии, релиза у которой ещё нет, берётся из `release-notes/<тег>.md` — именно
так она и попадает в CHANGELOG до тега.
